# AGENTS.md — OVERVODKA (Codex / Agent Guide)

Этот файл — **единая точка входа** для агента по проекту OVERVODKA.  
Цель: помогать с **Lua (vscripts)**, **Panorama UI**, и при необходимости **Node.js+MySQL**, сохраняя стиль проекта и не ломая существующий геймплей.

## 1) Что прочитать перед любой задачей (обязательно)
1. `AGENTS.md` (этот файл) — общий протокол работы.
2. `AGENT_RULES.md` — код-стандарты и запреты (строго соблюдать).
3. `AGENT_ONBOARDING.md` — ориентиры по структуре проекта.
4. Если задача про API/сервер: `api_contract.json` и `endpoint_map.json`.

## 2) Жёсткие ограничения (do / don't)
**НЕЛЬЗЯ:**
- Публиковать/логировать секреты (SERVER_KEY, токены, приватные URL).
- Делать массовые рефакторы “на всякий случай”, менять архитектуру без прямого запроса.
- Добавлять несуществующие методы Dota API. Если есть сомнения — предложить проверяемую альтернативу.

**НУЖНО:**
- Делать **минимальный дифф**, максимально локальные правки.
- Всегда добавлять `if not IsServer() then return end` в серверные хуки.
- Всегда использовать `GetAbsOrigin()` (не `GetOrigin()`).
- Чистить партиклы/таймеры, не оставлять утечки.
- В motion-контексте **не** использовать `SetForwardVector` (использовать `FaceTowards` или аналог после окончания motion).

## 3) Протокол работы агента (как выполнять задачи)
Всегда придерживаться этой последовательности:

1) **Сформулировать цель**  
   - Что именно надо изменить? (логика/баланс/баг/UX)
   - Какие файлы затрагиваются? (Lua/KV/локализация/Panorama)

2) **Найти точки входа в коде**  
   - Поиск по имени способности/модификатора/ивента.
   - Для UI: `custom_ui_manifest.xml`, `scripts/custom_game/*.js`, `layout/*.xml`.

3) **План изменений (коротко)**  
   - 3–6 пунктов: что меняем, где, какие риски.

4) **Имплементация**  
   - Патч в виде диффа или заменяемых функций.
   - Если добавляется модификатор — `LinkLuaModifier` сверху файла.

5) **Валидация** (минимум)  
   - Нулл-чеки, server guards, нет утечек.
   - Нет `GetOrigin()` в новом коде.
   - Если UI ↔ Lua: события совпадают по имени и payload.

6) **Итог**  
   - Список изменённых файлов.
   - Что тестировать в игре (2–5 пунктов).

## 4) Типовые задачи и как их делать

### A) Изменение/добавление способности (Lua + KV + локализация)
**Чек-лист:**
- Lua: ability class + modifiers (в одном файле или рядом, но с `LinkLuaModifier`).
- KV: `AbilitySpecial` для всех новых параметров.
- Локализация: `dota_tooltip_ability_*` + описание + спец-значения (если показываются).
- Эффекты: precache и корректная очистка.

**Никогда не “угадывать” SpecialValue**, если можно быстро найти существующий в KV. Если отсутствует — добавить и явно перечислить в ответе.

### B) Panorama UI (меню, панели, HUD)
**Чек-лист:**
- Обновить/подключить layout XML при необходимости (через `custom_ui_manifest.xml`).
- JS: не создавать бесконечные таймеры/think-loop без `$.Schedule` cancel-логики.
- Использовать `CustomNetTables` для состояния, а не спамить событиями.
- Стиль: придерживаться текущей структуры `content/overvodka/panorama/...`.

### C) Связка Panorama ↔ Lua (самый частый “стык”)
Есть два основных канала связи:

1) **События (RPC-подобно)**
- Panorama → server:
  - `GameEvents.SendCustomGameEventToServer("event_name", data)`
- Lua server:
  - `CustomGameEventManager:RegisterListener("event_name", function(_, keys) ... end)`

2) **CustomNetTables (состояние/данные)**
- Lua:
  - `CustomNetTables:SetTableValue("table_name", key, data)`
- Panorama:
  - `CustomNetTables.SubscribeNetTableListener("table_name", callback)`

**Правило:**  
- “Команда”/действие → Events  
- “Состояние”/данные → NetTables

### D) Backend / API (Node.js + MySQL)
- Сверяться с `api_contract.json` (эндпоинты, required-поля).
- При добавлении/изменении эндпоинта обновлять **оба**: `api_contract.json` и `endpoint_map.json`.
- На стороне Lua помнить: запросы дополняются `GameKey = SERVER_KEY`, метод — POST, JSON-ответ.

## 5) Соглашения по качеству (Definition of Done)
Изменение считается “готовым”, если:
- Не сломало существующую логику (минимальный дифф, совместимость).
- Нет утечек (партиклы, таймеры, thinker-энтити).
- Нет ошибок по entity validity (`IsNull`, `IsValidEntity`, `IsAlive`).
- В UI нет “вечных” Schedule без остановки.
- Для фичи, которая затрагивает несколько слоёв, совпадают:
  - имена эвентов,
  - формат payload,
  - имена NetTable и ключи.

## 6) Формат ответа агента (как писать результат)
- Сначала: **короткий план** (3–6 пунктов).
- Потом: **патч/дифф** по файлам.
- Потом: “что протестировать”.
- Если пришлось сделать допущение (например, путь KV/локализации неизвестен) — отметить явно.
